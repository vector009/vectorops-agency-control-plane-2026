# VectorOps Architecture Source of Truth

Source: `/home/ubuntu/upload/Text_to_PDF_Onlinenotpad.pdf` (33-page user-provided PDF, inspected 2026-09-14).

VectorOps is a multi-tenant AI automation agency operating system with two faces: an Agency Command Center for the owner and a custom-feeling client business portal. One React/Vite/TypeScript application, one Supabase project/database, tenant separation through Supabase RLS plus controlled server functions, and n8n as the execution engine.

The architecture has three logical planes. The Business Plane handles clients, accounts, onboarding, billing, partial payments, renewals, discounts, credits, free days, goodwill extensions, support, tasks, portals, analytics, reporting, and audit. The Automation Control Plane communicates with n8n to connect and verify instances, discover/deploy workflows, activate/deactivate where supported, apply client automation settings, control desired state, and synchronize actual state. The Execution Plane is n8n itself: triggers, integrations, APIs, AI, workflow logic, and execution.

The two explicitly required layers are Client Portal Configuration and Client Automation Control. Billing must support partial payments. The client side needs identity, branding, dashboard, KPIs, modules, automation views, business metrics, reports, and controls. Conceptual routes are `/app/admin` and `/app/client/<slug>`; current implementation routes `/admin` and `/portal/<slug>` are acceptable equivalents.

Authentication has two roles, admin and client. The current user-approved login model is retained: admin password-only login tied internally to the existing Supabase Auth admin identity; clients use a portal slug and password; credentials are verified server-side; sessions are HttpOnly; tenant data is scoped by profile/client_id and the portal slug.

Important implementation rule: do not use public anonymous Supabase reads for admin data because RLS correctly denies them. Admin reads/writes must go through protected server functions after verifying the admin session. Client reads/writes must go through tenant-bound server functions or authenticated Supabase sessions and must never accept an untrusted client_id from the browser.

Additional requirements from pages 6–10: VectorOps must never store client passwords in the application database; Supabase Auth owns password handling. Client onboarding provisions the client account using the onboarded email and gives the client credentials/access. A unique slug resolves each client portal without custom DNS. `client_portal_config` must cover identity (slug, logo, favicon, portal title, company display name), appearance (primary/secondary colors and visual preferences), enabled modules, dashboard widget arrangement/visible cards/order/sections, and KPI configuration. Customization is business-specific rather than only logo/color. Admin navigation must include Overview, Clients, Automations, Money, Calendar, Tasks, Support, Infrastructure, Activity, Audit, Settings. Overview KPIs include active clients, MRR, collected/outstanding/overdue revenue, upcoming renewals, open tickets, workflow failures, and infrastructure issues, with Revenue Trend, Attention Required, Renewals, Client Health, and Automation Health areas. Attention engine examples include overdue payment, renewal approaching, workflow failure, degraded n8n, stale telemetry, expiring credential, waiting support ticket, incomplete onboarding, and failed client automation control. Client management must support create, view, edit, pause, churn, reactivate. Onboarding is a wizard beginning with company, contact, email, phone, notes.

Verified schema support already exists for the architecture: `client_portal_config` includes branding, enabled_modules, dashboard_config, kpi_config, terminology, and client_settings_schema; `client_automation_controls` includes desired_state, actual_state, sync_status, requested_by_user_id, and control error fields; `workflows` has client/n8n identity plus desired/actual state; `discovered_workflows` supports unassigned discovery; `automation_templates` supports deployment templates; `client_onboarding` includes identity/portal/commercial/infrastructure/automations/n8n/account/verification stages; `client_reports` supports client-visible reports; `subscriptions`, `invoices`, `payments`, and `billing_adjustments` support partial payments and adjustments; `n8n_instances` stores only `n8n_api_secret_ref`, not raw secrets; `credentials` stores Vault references only.

Final architecture rules: audit client creation, subscription changes, payments, invoice changes, adjustments, connection changes, churn, and workflow assignment. Client health should distinguish operational, relationship, and billing health. Churn is safe and preserves historical data: mark client churned, disconnect connections, cancel/non-renew subscriptions, block portal access. Reactivation is deliberate: review subscription, reconnect infrastructure, restore automation, verify telemetry, resume service. Security boundary is authentication → role → RLS → tenant data, with sensitive operations in controlled server functions. New-client flow is identity, slug, portal config, subscription, shared/dedicated infrastructure, n8n connection, then workflow templates. Client flow is login, personalized portal, overview/results, automation performance, approved setting change, desired state, and n8n control-layer application. Admin sees client, subscription, money, automation, infrastructure, support, tasks, and health in one place.
